# 架构说明与关键取舍

## 总览

两个项目都遵循同一条产品链路：

```text
用户意图 → 任务理解 → 检索或工具调用 → 结果组织 → 可理解的输出
```

区别在于：

- RAG 文档问答重点解决“答案是否有资料支撑”。
- 命理 Agent 重点解决“面对不同意图时，系统应该调用什么能力”。

## RAG 文档问答

### 主链路

```text
文件上传
  → 文件类型识别
  → 文档加载与切分
  → Ollama bge-m3 向量索引 + BM25 索引
  → 查询改写
  → 相关性过滤
  → 大模型生成
  → RAGAS 评估
```

### 关键取舍

| 决策 | 原因 | 代价 |
| --- | --- | --- |
| 向量检索与 BM25 并用 | 语义相似与关键词精确命中各有盲区，混合检索可以互补 | 索引与调试复杂度增加 |
| 用 Ollama `bge-m3` 本地生成向量 | 不依赖收费嵌入接口，便于本地演示 | 首次运行需要安装 Ollama 和模型 |
| 在生成前加入查询改写和过滤 | 减少无关上下文进入模型，提高回答可解释性 | 增加模型调用次数和延迟 |
| 演示阶段暂不接入独立重排 | 外部重排服务额度受限，优先保证链路可运行 | 候选结果排序能力可能受限，后续需对比验证 |
| 使用 RAGAS 评估 | 不只观察“回答像不像”，还要检查上下文与忠实度 | 评估依赖带参考答案的数据集 |
| 采用 Gradio 快速搭建交互 | 能较快验证产品体验和检索流程 | 当用户量或权限需求提升后，需要更完整的前后端方案 |

### 适合继续展示的内容

- 同一份资料在纯模型模式与 RAG 模式下的回答差异。
- 修改问题表述后，查询改写与过滤是否带来更稳定的上下文。
- 没有相关资料时的拒答行为。
- RAGAS 指标的计算方式和指标之间的区别；没有实测分数时不展示虚构数字。

## 命理 Agent

### 主链路

```text
前端对话
  → FastAPI 接口
  → Agent 判断意图
  → 选择工具
  → 获取本地知识或外部服务结果
  → 模型组织回答
  → 写入会话历史
```

### 工具划分

| 工具 | 用途 | 边界 |
| --- | --- | --- |
| 本地知识库 | 查询风水常识 | 由 Ollama `bge-m3` 生成向量，只依据已索引内容回答 |
| 八字测算 | 根据姓名与出生信息生成八字结果 | 依赖外部服务，需校验输入 |
| 每日占卜 | 返回占卜内容 | 明确定位为娱乐演示 |
| 解梦 | 提取梦境关键词并查询解释 | 不把结果解释为确定事实 |
| 答案边界 | 本地资料无法确认时明确拒答 | 不提供实时搜索，避免引入额外依赖与不可控来源 |

### 关键取舍

| 决策 | 原因 | 代价 |
| --- | --- | --- |
| 用 Agent 路由多个工具 | 比把全部规则写进一个提示词更容易扩展和定位问题 | 工具选择可能出错，需要边界提示和兜底 |
| 对话模型使用 DeepSeek，嵌入使用本地 `bge-m3` | 生成能力与检索能力解耦，本地向量不消耗模型额度 | 需要同时维护云端凭据与本地 Ollama |
| 用 Redis 保存会话 | 支持多轮对话和独立会话标识 | 增加部署依赖和会话生命周期管理 |
| 外部能力封装成工具 | 对模型隐藏接口细节，便于替换和测试 | 每个工具仍需单独处理超时、错误和输入校验 |
| Docker 化部署 | 降低环境差异，方便演示和复现 | 镜像、密钥和持久化目录需要独立管理 |

## 共同的产品化原则

1. **输出要能解释**：系统不仅给答案，还应让人知道答案来自资料、工具还是模型本身。
2. **失败要可理解**：外部接口失败时，用户需要看到清晰提示，而不是内部异常。
3. **能力要有边界**：无法确认的信息应明确拒答或提示局限性。
4. **效果要能验证**：用固定样例、异常输入和可比较指标检查系统，而不是只凭一次演示判断。
